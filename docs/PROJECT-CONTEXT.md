# 共通知識の棚：Markdown資料を登録して必要なものだけ読む

## 何を用意したか

```text
project-context/
  catalog.json          登録台帳：場所・状態・版・適用範囲
  overview.md           目的・対象外・制約・完了条件
  glossary.md           用語・略語・別名・区別する言葉
  requirements.md       必須機能・禁止事項・例外・完了条件
  design/overview.md    設計書の入口
  decisions.md          決定と理由・見送った案
  questions.md          未確認事項・矛盾・確認方法
```

全資料が**未記入のテンプレート／検討中**で始まります。
このキットの作例を、実際の業務の正式仕様として扱うものではありません。
空の表も「要件なし」「未確認事項なし」「検査済み」の証拠ではありません。

別の開発プロジェクトを `--root` にする場合は、その直下へ `project-context/` を配置します。既存ファイルは上書きせず比較・統合してください。キット本体を `tools/` にコピーしただけでは、別プロジェクトの台帳は作られません。

## まず試す

Copilot のエージェントチャットで：

```text
kit_contextで共通知識の一覧を見せてください。本文はまだ読まないでください。
```

`/context-overview` でも確認できます。登録した場所・状態・版・適用範囲と、本文を出力した記録が表示されます。
今回は用語集だけが必要なら、次のように依頼します。

```text
kit_contextで action=read、id=glossary を指定して用語集だけ読んでください。
他の資料はまだ読まないでください。
```

ターミナルでも同じルートを対象に確認できます。

```sh
node src/cli.mjs context --format text
node src/cli.mjs context-read glossary
```

別の開発プロジェクトへ組み込んだ場合は、そのプロジェクトを `--root` で指定してください。
サーバー起動後にキットを更新した場合は、MCPサーバーを再起動し、ツール一覧に `kit_context` があるか確認してください。

## ファイルを用意する方法は2つ

### A. 同梱の入力欄へ書く

目的は overview.md、用語は glossary.md、要件は requirements.md、設計は design/overview.md へ記入します。
AIに案を作らせても、利用者が確認するまでは検討中のままです。

### B. すでにあるMarkdown資料の場所を登録する

コピーを増やさず、catalog.json の documents に既存ファイルへの相対パスを登録できます。
例えば、対象プロジェクト内の `docs/design.md` を登録する項目は次の形です。

```json
{
  "id": "existing-design",
  "title": "既存の設計書",
  "kind": "design",
  "path": "docs/design.md",
  "status": "draft",
  "version": "0.1",
  "scope": "対象機能を記入"
}
```

これは項目の例です。台帳全体をこの項目だけで上書きせず、既存の documents 配列へ追加します。
登録先はワークスペース内の `.md` ファイルに限ります。ルート外、代表的な秘密ファイル、禁止パスは登録しても読み取れません。
同じID・同じ場所の重複登録は拒否します。別名のシンボリックリンクが同じ実体を指す場合も、曖昧な正式性を付けず警告します。

## 台帳の項目

| 項目 | 内容 |
| --- | --- |
| id | ツールで選ぶ短いID。半角英小文字・数字・ハイフン・アンダースコア |
| title | 分かりやすい表示名 |
| kind | overview / glossary / requirements / design / decisions / questions |
| path | 対象ルートからのMarkdownファイルの相対パス |
| status | official（正式）/ draft（検討中）/ archived（過去版） |
| version | 利用者が指定する版。正式扱いにする場合は「未設定」のままにしない |
| scope | 適用範囲。例：全体、対象の機能名 |

**「正式」は利用者の宣言であり、プログラムが内容を検証したという意味ではありません。**
状態をAIが勝手に正式化したり、更新日時が新しいだけで優先したりしないよう、プロンプトでも指示しています。
版や範囲の違う資料が矛盾する場合、勝手にどちらかを採用せず questions.md へ確認案を残します。

## 参照状態の意味

| 表示 | 意味 |
| --- | --- |
| 登録のみ・本文未出力 | 登録はあるが、このキットで本文を返す準備をした記録がない |
| 原文の場所のみ出力 | 大きすぎるため本文を返さず、保存版への入口だけを返した |
| 本文の一部を出力した記録あり | ページ取得などで一部だけ返す準備をした |
| 本文全体を出力した記録あり | 同一の保存版・台帳条件で、全文を返す準備をした記録がある |
| 要再確認 | 内容や台帳条件が変わった、保存版が取得できない等 |
| 元ファイル／出力記録を確認できない | 取得失敗を確認済みへ置き換えず、そのまま表示 |

これらは**キット側のツール／CLI出力準備の記録**です。
通信の完了、AIが受け取ったこと・理解したこと、内容の正しさ、人の承認の保証ではありません。
VS Code内蔵の別ツールで読んだ内容も自動追跡しません。記録がないことは、会話中に一度も読まれていないという証明でもありません。

一覧表示は変更検知のために登録ファイルをローカルでハッシュ確認しますが、本文を一覧に含めません。
このローカル確認だけでは「本文を出力した記録」を付けません。

## 何が変わると再確認になるか

- 登録資料の本文が変わった。
- 版・状態・適用範囲・場所など、登録内容が変わった。
- 根拠の原文保存版が期限切れ・削除済み・不一致になった。
- 元ファイルや出力記録を取得できなくなった。

必要な資料を明示的に読み直してから再開します。
異なる版・異なる台帳条件の部分取得を、まとめて「全文を確認した」とは扱いません。

## 未確認事項・矛盾の記録

questions.md に、不明点・関係する根拠・確認方法・確認結果を分けて残せます。
`/context-question-propose` は、今回の会話で実際に見つかった内容から追記案を作るためのプロンプトです。
**利用者が承認するまではファイルを書き換えない**指示になっています。

自動で全資料の意味を解析し、矛盾を漏れなく検出する機能ではありません。
未確認事項を「確認済み」に変えるときも、人の確認と根拠を残してください。

## 圧縮状況との関係

一覧を返す情報もトークンを使い得るため、`kit_stats` の参考比較に一覧の返却テキストのバイト数を追加しました。
文字数・バイト数と、Copilotの実トークン数・請求額は別です。
用語集を登録しても、モデルの語彙に新しい1トークンが追加されるわけではありません。

この段階では、作業種別をAIが自動判定する参照セット・PDF/Word変換・意味的な矛盾の完全自動検出は実装していません。

## 機密情報と削除

- 実業務の要件・設計・用語は機密になり得ます。GitHubの公開範囲を確認し、必要なら実資料を追跡対象外にしてください。
- 元ファイルを自動でGitHubへ送る機能はありません。今回公開するのは空の入力用テンプレートです。
- 原文保存版・出力記録は `.context-kit-cache/` に保存し、ソース管理から除外します。
- `purge` は原文保存版・統計・出力記録を消します。台帳・Markdown資料・引き継ぎメモは消しません。
- 複数プロセスが同じ台帳を同時更新した場合、記録の一部を失う可能性があります。安全な初期運用では、同じルートにサーバーを重複登録しないでください。
